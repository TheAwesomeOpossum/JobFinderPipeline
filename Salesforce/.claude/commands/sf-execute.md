# /sf-execute — Single Phase PIV Execution

This command executes a SINGLE PHASE of a Salesforce implementation plan through a complete PIV (Plan-Implement-Validate) loop with three tiers of testing.

---

## Phase 0: Pre-Flight

### Step 0a: Parse Arguments

1. Parse `$ARGUMENTS` for phase plan file path
   - If no argument: scan `projects/**/phase-*.md` for the most recent unexecuted phase plan
   - If still none: "No phase plan found. Run `/sf-plan-feature projects/{alias}/{feature}/requirements.md` first."

### Step 0b: Read Phase Plan

2. Read the phase plan file in full

### Step 0c: Extract Phase Metadata

3. Extract the following from the phase plan:
   - Feature name, org alias, phase number, total phases
   - Master plan path
   - Prior Phase Summary (understand what already exists in org)
   - Task list (all TASK items)
   - Testing framework (Tier 1, 2, 3 specifications)
   - Skill & context references

### Step 0d: Confirm Org Connection

4. Confirm org connection:
   ```bash
   sf org display --target-org {alias}
   ```
   - If connection fails: "Cannot connect to org '{alias}'. Check your authentication and try again."

### Step 0e: Verify Project Structure

5. Verify `force-app/main/default/` directory exists
   - If missing: "Project directory structure not found. Ensure you are in a valid SFDX project root."

### Step 0f: Load Skills and Context

6. Load referenced skills and context files
   - Read each skill's `SKILL.md` referenced by the phase plan
   - Load relevant context files from `context/{alias}/` as specified in the plan
   - If a referenced skill or context file is missing: warn but continue

### Step 0g: Initialize Issue Log

7. Create an in-memory Issue Log to track problems encountered during this PIV loop. Every time a deploy fails, a test fails, an E2E scenario fails, or Claude makes an autonomous decision, add an entry:
   ```
   Issue Log Entry:
   - Tier: {Implement / Tier 1 / Tier 2 / Tier 3}
   - Issue: {what went wrong}
   - Root Cause: {why it happened}
   - Resolution: {what was done to fix it}
   - Attempts: {how many tries to resolve}
   ```
   Also log autonomous decisions:
   ```
   Decision Log Entry:
   - Context: {what prompted the decision}
   - Decision: {what Claude decided}
   - Rationale: {why}
   ```
   This log feeds into the Phase Retrospective presented to the user in Tier 3 (Step 4d).

### Step 0h: Optional Baseline Regression (Recommended for first phase or after a gap)

8. Ask the user:
   ```
   Would you like to run a baseline regression before implementation begins? (recommended / skip)

   Why: Running RunLocalTests now captures any pre-existing test failures so they aren't
   confused with regressions caused by this phase's changes.
   ```
   - If **recommended / yes:** run `sf apex run test --test-level RunLocalTests --target-org {alias} --wait 10 --json`
     - Parse and display results: how many tests exist, how many are currently failing
     - Record all currently-failing tests in the Issue Log as "pre-existing failures" so they are not flagged as new regressions during Tier 1
     - Display: "Baseline: {N} tests, {F} pre-existing failures noted. These will not be counted as new regressions."
   - If **skip:** proceed without baseline. Note in Issue Log: "No baseline run — pre-existing failures unknown."

### Step 0i: Display Phase Start

9. Display: "Starting Phase {N} of {M}: {Phase Name} | {task count} tasks"

---

## Phase 1: Implement

Process each TASK in the task list sequentially.

### For each TASK:

1. **Load skill pattern** — Read the referenced skill pattern (if specified in the task)
2. **Generate metadata/code** — Generate the metadata or code file using skill templates and org naming conventions
3. **Deploy to org:**
   ```bash
   sf project deploy start --metadata "{type}:{name}" --target-org {alias} --wait 10
   ```
4. **If deploy succeeds:** Mark task complete, move to next task
5. **If deploy fails:**
   - Display the error message
   - Cross-reference with the relevant skill's "Common Deploy Errors" section
   - Suggest a fix based on the error pattern
   - Apply fix and retry (max 2 automatic retries)
   - If still failing after 2 retries: ask user —
     ```
     Deploy failed after 2 attempts. Choose:
     1. Debug together
     2. Skip this task
     3. Abort phase
     ```

### Field Completeness Audit

Before the user checkpoint, scan the completed task list for any field deployment tasks. If any CustomField was deployed in this phase, run these three checks:

**1. FLS check** — Was a Profile or PermissionSet task also completed that covers the new fields?
- If YES: proceed
- If NO: warn —
  ```
  ⚠️ FLS Gap Detected: {N} field(s) were deployed but no Profile/PermSet FLS update was found
  in the task list. Deploying a field does NOT auto-grant FLS to any profile.

  Missing FLS for: {list of fields and their objects}

  Options:
  1. Add FLS now (retrieve Admin profile, add fieldPermissions, deploy) — recommended
  2. Skip — I'll handle FLS separately
  ```
  If the user chooses option 1: retrieve the Admin profile, add the missing `<fieldPermissions>` blocks, deploy, then re-check.

**2. Layout check** — Was a Layout task also completed that covers the affected objects?
- If YES: proceed
- If NO: warn —
  ```
  ⚠️ Layout Gap Detected: {N} field(s) were deployed but no Layout update was found
  in the task list. New fields are not visible on record pages until added to a layout.

  Missing layout coverage for: {ObjectName} — fields: {list}

  Options:
  1. Update layout(s) now (discover layouts, retrieve, add fields, deploy) — recommended
  2. Skip — I'll update layouts separately
  ```
  If the user chooses option 1: query for all layouts on the object via Tooling API, retrieve each, add the new fields, deploy.

**3. Picklist RT check** — Were any Picklist or MultiselectPicklist fields deployed?
- If YES: for each affected object, run:
  `sf data query --query "SELECT DeveloperName FROM RecordType WHERE SobjectType = '{ObjectApiName}'" --target-org {alias}`
  - If Record Types exist: warn —
    ```
    ⚠️ Picklist RT Check Required: New picklist field(s) on {ObjectName} — this object
    has {N} Record Type(s). Picklist values must be explicitly enabled per Record Type.

    Record Types found: {list}

    Options:
    1. Check and update RecordType picklist values now
    2. Skip — I'll verify picklist RT availability separately
    ```
  - If no Record Types: proceed silently
- If NO picklist fields: skip this check

After any gap remediation completes, proceed to the user checkpoint.

### Implementation Complete Checkpoint

After all tasks complete (including any Field Completeness Audit remediation):
- Display: "Implementation complete. {N}/{M} tasks deployed successfully."
- **User checkpoint:** "Ready to begin testing? (yes / review what was deployed first / abort)"
  - If "review": display list of all deployed components with metadata types
  - If "abort": stop execution, display what was deployed so far
  - If "yes": proceed to Phase 2

---

## Phase 2: Validate — Tier 1 (Unit Tests)

### Step 2.0: Determine Tier 1 Applicability

**Not every phase requires unit tests.** Check the task list: does this phase produce any Apex classes or Flows?

- **If YES (Apex or Flows present)** → proceed to Step 2a (full Tier 1)
- **If NO (declarative-only: objects, fields, VRs, permsets, layouts, FlexiPages, tabs)** → skip test generation but still run regression:
  ```bash
  sf apex run test --test-level RunLocalTests --target-org {alias} --wait 10
  ```
  - If regression passes: display "Tier 1: SKIPPED (declarative-only phase). Regression: {N} tests passed." → proceed to Tier 2
  - If regression fails: a declarative change broke existing code. Display failures, investigate, fix before proceeding.

**What to write Apex tests for:**
| YES — write tests | NO — do NOT write tests |
|---|---|
| Apex triggers, handlers, processors | Custom objects/fields (verify via `sf sobject describe`) |
| Batch, Schedulable, Queueable classes | Page layouts, FlexiPages (verify via E2E/UI) |
| REST/SOAP endpoints | Permission sets/profiles (test EFFECT via `System.runAs()`) |
| Service, Utility, Controller classes | Custom tabs, apps, navigation |
| Invocable methods (@InvocableMethod) | Email templates, reports, dashboards |
| Flows — INDIRECTLY via DML that triggers them | LWC components (use Jest, not Apex) |
| Validation rules — INDIRECTLY via DmlException (only if interacting with Apex) | VRs as standalone (verify in Tier 2 E2E instead) |

**Anti-patterns to avoid:**
- Writing test classes for declarative-only phases
- Testing that a field exists (use `sf sobject describe`)
- Testing getter/setter methods with no business logic
- Using `SeeAllData=true` (creates org-data dependency)
- Testing Salesforce platform behavior (lookups work, picklists save, etc.)

### Step 2a: Generate Test Classes (only if Tier 1 applies)

- Read the Testing Framework → Tier 1 section from the phase plan
- For each test class specified:
  - Load the relevant skill for test patterns:
    - `sf-trigger-patterns` for trigger/handler tests
    - `sf-apex-classes` for other Apex class tests
  - Generate the test class file with:
    - `@isTest` annotation on the class
    - `@TestSetup` method with test data factory (reusable test data creation)
    - One `@isTest` method per scenario listed in the plan
    - Bulk test with 200+ records
    - `Test.startTest()` / `Test.stopTest()` boundaries around the code being tested
    - `System.assertEquals` / `System.assertNotEquals` assertions with descriptive messages
  - Write to `force-app/main/default/classes/{TestClassName}.cls` + corresponding `.cls-meta.xml`
  - **One test class per Apex class** — if testing a handler and its processor, one test class covers both unless complexity demands separation

### Step 2b: Deploy Test Classes

```bash
sf project deploy start --metadata "ApexClass:{TestClassName}" --target-org {alias} --wait 10
```
- Deploy each test class
- If deploy fails: apply same retry logic as Phase 1 (2 auto-fix attempts, then ask user)

### Step 2c: Run New Tests (Quick Feedback)

```bash
sf apex run test --class-names {comma-separated-new-test-classes} --target-org {alias} --wait 10 --json
```
- Parse results: pass/fail per method, coverage per class
- **If ALL pass:** proceed to regression testing (Step 2d)
- **If ANY fail:**
  - Display: test method name, error message, stack trace
  - Attempt to fix the code (read the error, modify the source or test, redeploy)
  - Re-run failed tests (max 2 auto-fix attempts)
  - If still failing after 2 attempts:
    ```
    Test {method} is failing.
    Error: {detail}
    Stack trace: {trace}

    Want me to try a different approach, or shall we debug together?
    ```

### Step 2d: Run Full Regression Tests

```bash
sf apex run test --test-level RunLocalTests --target-org {alias} --wait 10 --json
```
- This runs ALL test classes in the org — not just new ones
- Parse results and compare against the regression test list from the phase plan
- Categorize failures:
  - **New code broke old test** → high priority, must fix before proceeding
  - **Old test was already failing** → note it, ask user if it's a known issue
  - **Flaky test** → re-run once, if passes then proceed
- If regression failures caused by new code:
  - Fix the new code (not the old test)
  - Redeploy modified components
  - Re-run both new tests and full regression
  - Must ALL pass before proceeding

### Step 2e: Coverage Check

- Parse coverage report from test results JSON
- Check: new classes have ≥85% coverage
- Check: org-wide coverage ≥75%
- If below threshold:
  - Identify uncovered lines
  - Suggest additional test scenarios to cover them
  - Generate additional test methods
  - Redeploy test class and re-run

### Tier 1 Gate

**ALL of the following must be true to pass Tier 1:**

| Criterion | Required |
|---|---|
| New test failures | 0 |
| Regression test failures | 0 |
| New class coverage | ≥85% |
| Org-wide coverage | ≥75% |

- Display: "Tier 1 PASSED: {N} tests passed, {P}% coverage on new classes, {Q}% org-wide"
- Proceed to Tier 2

---

## Phase 3: Validate — Tier 2 (E2E Testing)

### Step 3a: Determine E2E Approach

- Check if agent-browser skill is available in `skills/agent-browser/SKILL.md`
- **If available:** Attempt browser automation
  1. Launch browser, navigate to org login URL
  2. If login succeeds (no MFA/SSO block): use browser automation for all scenarios
  3. If login fails (MFA prompt, SSO redirect, etc.): fall back to guided CLI
- **If not available:** Use guided CLI approach

### Step 3b: Execute E2E Scenarios

Read E2E scenarios from the phase plan's Tier 2 section.

**For each scenario:**

#### Browser Automation Approach

1. Navigate to the relevant page in Salesforce
2. Perform the steps (click New, fill fields, save, etc.)
3. Take screenshots at key points (before action, after action, error states)
4. Run verification queries:
   ```bash
   sf data query --query "{verification SOQL}" --target-org {alias} --json
   ```
5. Compare actual vs expected results
6. Mark: PASS or FAIL with details and screenshot references

**Field existence verification — always use Tooling API:**

When verifying that a custom field was deployed, especially on standard objects (Account, Contact, Opportunity, Product2, etc.), the standard SOQL `FieldDefinition` object is unreliable and may return no results. Use the Tooling API instead:

```bash
# Verify a custom field exists on any object
sf data query \
  --query "SELECT Id, DeveloperName, EntityDefinition.QualifiedApiName FROM FieldDefinition WHERE EntityDefinition.QualifiedApiName = '{ObjectApiName}' AND DeveloperName = '{FieldDeveloperName}'" \
  --use-tooling-api \
  --target-org {alias}
```

Note: `DeveloperName` does NOT include the `__c` suffix. Use `Cost_Category` not `Cost_Category__c`.

**Formula field verification when no live data exists:**

When the sandbox has no records to trigger formula evaluation, verify the formula definition text directly:

```bash
sf data query \
  --query "SELECT Id, DeveloperName, Metadata FROM CustomField WHERE EntityDefinition.QualifiedApiName = '{ObjectApiName}' AND DeveloperName = '{FieldDeveloperName}'" \
  --use-tooling-api \
  --target-org {alias}
```

#### Guided CLI Approach

1. Display step-by-step instructions to the user:
   ```
   E2E Scenario 1: {Scenario Name}

   Please perform these steps in your org:
   1. Navigate to {tab/page}
   2. Click "{button}"
   3. Fill in: {field list}
   4. Click "Save"

   Tell me the record ID when done (or paste the URL).
   ```
2. After user confirms: run verification queries
   ```bash
   sf data query --query "{verification SOQL}" --target-org {alias} --json
   ```
3. Compare actual vs expected
4. Mark: PASS or FAIL

### Step 3c: Handle E2E Failures

- If a scenario fails:
  - Display what was expected vs what actually happened
  - Diagnose: query org state, check deploy logs, check flow debug logs
    ```bash
    sf data query --query "SELECT Id, ... FROM {object} WHERE ..." --target-org {alias} --json
    ```
  - Fix the root cause (modify code/metadata, redeploy)
  - **Must re-run Tier 1** after any code changes (regression safety)
  - Re-run the failed E2E scenario

### Tier 2 Gate

**ALL scenarios must pass.**
- Display: "Tier 2 PASSED: {N}/{N} E2E scenarios verified"
- Proceed to Tier 3

## Phase 4: Validate — Tier 3 (User Review)

### Step 4a: Code Review

Display the code review checklist from the phase plan:

```
Code Review Checklist:

[ ] {HandlerClass}.cls
    - Follows org's handler pattern (TriggerHandlerInterface)
    - Bulk-safe (no SOQL/DML in loops)
    - Recursion guard implemented

[ ] {ProcessorClass}.cls
    - Business logic is correct
    - Error handling appropriate

[ ] {TestClass}.cls
    - Covers all required scenarios
    - Bulk test with 200+ records
    - Negative test cases included

Would you like me to display any of these files for review? (file name / all / skip)
```

- If user asks to see a file: display the full file content
- If user asks for diffs: show what was added/changed in this phase
- If user says "skip": proceed to declarative review

### Step 4b: Declarative Review

```
Declarative Review Checklist:

[ ] {FlowName} flow
    - Entry conditions are correct
    - Element logic matches requirements
    - No unintended side effects

[ ] {ValidationRuleName} validation rule
    - Formula logic is correct
    - Error message is user-friendly

[ ] No conflicting automation introduced on {ObjectName}

Would you like me to show flow details or validation rule formulas? (name / all / skip)
```

- If user asks to see details: display the flow structure or validation rule formula
- If user says "skip": proceed to user E2E testing

### Step 4c: User E2E Testing

```
User E2E Testing:

Please perform these tests yourself in the org:

[ ] {Scenario 1 description}
[ ] {Scenario 2 description}
[ ] {Scenario 3 description}
[ ] {Scenario 4 description}

Report results: all passed / {list failures}
```

- Wait for user response
- If "all passed": proceed to approval
- If user reports failures: capture details and proceed to Step 4d feedback handling

### Step 4d: Phase Retrospective

Before asking for approval, present a transparent summary of everything that happened during this PIV loop — including all problems encountered and how they were resolved. This gives the user full visibility into Claude's decision-making process.

**Build the retrospective from the Issue Log** (accumulated throughout Phases 1-3):

```
## Phase {N} Retrospective

### Implementation Summary
- Tasks completed: {N}/{M}
- Components deployed: {list}
- Test classes created: {N} (or: none — declarative-only phase)

### Issues Encountered & Resolutions

| # | Tier | Issue | Root Cause | Resolution | Attempts |
|---|---|---|---|---|---|
| 1 | Implement | Deploy failed: "Cannot deploy Profile before field exists" | Field deploy order wrong | Reordered: deployed fields before profile update | 1 |
| 2 | Tier 1 | testBulkInsert200 failed: "Too many SOQL queries: 101" | SOQL inside for loop in StatusProcessor.execute() | Moved query outside loop, used Map for lookup | 2 |
| 3 | Tier 1 | Regression: AccountTriggerHandlerTest failed | New Invoice__c trigger re-fired Account trigger via lookup | Added recursion guard check in InvoiceTriggerHandler | 1 |
| 4 | Tier 2 | E2E-2: Invoice Total showed 0 instead of sum | Flow assignment used wrong variable | Fixed flow variable reference, redeployed | 1 |

_(or: No issues encountered — clean implementation)_

### Decisions Made During Execution
- {Any judgment calls Claude made, e.g., "Used SOQL query outside loop instead of lazy-loading because record count is always <50"}
- {Any deviations from the plan, e.g., "Added an extra field Status_Reason__c not in the original plan because the VR required it"}

### Test Results Summary
- Tier 1: {N} tests passed, {P}% coverage | {Skipped — declarative only}
- Tier 2: {N}/{N} E2E scenarios passed
- Tier 3: Pending user review ← (you are here)
```

**The user should review this retrospective carefully.** It shows:
- Problems Claude encountered and might have solved incorrectly
- Decisions Claude made autonomously that the user might disagree with
- Deviations from the original plan that need user awareness

### Step 4e: Collect User Approval

- After presenting the retrospective, wait for explicit approval: "Phase {N} approved" or similar
- **If user provides feedback or corrections based on the retrospective:**
  1. Implement the requested changes
  2. Redeploy modified components
  3. Re-run Tier 1 (full regression — ensure fixes don't break anything)
  4. Re-run affected Tier 2 scenarios
  5. Add the feedback and re-work to the Issue Log
  6. Present updated retrospective
  7. Return to Step 4e for re-approval
  8. Repeat until user approves

### Tier 3 Gate

**User must explicitly approve after reviewing the retrospective.**
- Display: "Tier 3 PASSED: User approved Phase {N}"

## Phase 5: Complete

### Step 5a: Read Master Plan

- Read the master plan using the path stored in the phase plan's header (`Master Plan:` field)
- Parse the Phase Registry, Regression Test Registry, Prior Phase Summaries, and Acceptance Criteria sections

### Step 5b: Update Phase Registry

- Set this phase's status to "Completed" with timestamp
- Set plan file path
- Example update:
  ```
  | Phase {N} | {Phase Name} | Completed | {YYYY-MM-DD HH:mm} | {plan-file-path} |
  ```

### Step 5c: Update Regression Test Registry

- Add all new test classes created in this phase:
  ```
  | {TestClassName} | Phase {N} | {ClassesCovered} | {timestamp} |
  ```
- This ensures future phases include these tests in regression runs

### Step 5d: Write Phase Summary

- Add to the Prior Phase Summaries section of the master plan:
  ```
  ### Phase {N} Summary (completed {timestamp})
  - Created: {list of objects/fields/classes/flows created}
  - Deployed: {count} components to {alias}
  - Tests: {N} test classes, {M} methods, all passing
  - Coverage: {P}% on new classes
  - Issues encountered: {count} ({brief list or "none"})
  - Key decisions: {brief list of any autonomous decisions made}
  ```

### Step 5e: Write Retrospective to Phase Plan

Append a `## Phase Retrospective` section to the bottom of the phase plan file (the file passed as `$ARGUMENTS`). This makes the issues, decisions, and test results permanently visible in the plan document for future reference.

```markdown
---

## Phase Retrospective

**Completed:** {YYYY-MM-DD HH:mm}
**Executed by:** Claude

### Implementation Summary

- Tasks completed: {N}/{M}
- Components deployed: {list}
- Test classes created: {list} _(or: none — declarative-only phase)_

### Issues Encountered & Resolutions

| # | Tier | Issue | Root Cause | Resolution | Attempts |
|---|---|---|---|---|---|
| 1 | {tier} | {issue} | {root cause} | {resolution} | {N} |

_(or: No issues encountered — clean implementation)_

### Autonomous Decisions Made

- {Decision 1: context → decision → rationale}
- {Decision 2: ...}

_(or: No autonomous decisions — followed plan exactly)_

### Test Results

| Tier | Result | Details |
|---|---|---|
| Tier 1 (Unit Tests) | PASSED / SKIPPED | {N} tests, {P}% coverage on new classes, {Q}% org-wide |
| Tier 2 (E2E) | PASSED | {N}/{N} scenarios verified |
| Tier 3 (User Review) | APPROVED | User approved {YYYY-MM-DD HH:mm} |
```

Build this section from the in-memory Issue Log accumulated throughout Phases 1–3. If the log is empty, write the "No issues encountered" / "No autonomous decisions" variants.

### Step 5f: Update Acceptance Criteria

- For each acceptance criterion addressed by this phase: update status
  - If fully addressed: mark "Complete"
  - If partially addressed: mark "Phase {N} done — remaining work in Phase {K}"

### Step 5g: Commit

- Display: "Phase {N} complete. Run `/sf-commit` to commit these changes?"
- If user confirms: suggest commit message that includes the implementation summary AND issues:

  ```
  feat(phase-{N}): {phase description}

  Metadata:
  - {Category}: {items}
  - {Category}: {items}

  Issues resolved:
  - {Issue 1 brief}: {resolution}
  - {Issue 2 brief}: {resolution}
  (or: No issues — clean implementation)

  Tests: {N} passed, {P}% coverage
  ```

  This creates a permanent git record of what happened during the phase, including problems and fixes — invaluable for future debugging and knowledge transfer.

- If user declines: note that changes are uncommitted

### Step 5h: Next Phase Guidance

- Check Phase Registry: are there remaining phases?
- **If yes:**
  ```
  Phase {N} of {M} complete. {M-N} phases remaining.
  Say 'generate next phase' or run `/sf-plan-feature --next {feature-name}` when ready.
  ```
- **If no (all phases done):**
  ```
  All {M} phases complete! Feature '{feature-name}' is fully implemented.
  Consider running `/sf-check-context-freshness {alias}` to update org context.
  ```

## Test Failure Handling Summary

| Tier | Failure Type | Action | Re-run Required |
|---|---|---|---|
| 1 | New test fails | Auto-fix (2 attempts), then ask user | Re-run new tests |
| 1 | Regression fails | Fix new code (not old test) | Re-run full regression |
| 1 | Coverage below threshold | Generate additional test scenarios | Re-run new tests |
| 2 | E2E scenario fails | Diagnose via queries, fix, redeploy | Tier 1 + failed Tier 2 |
| 3 | User feedback | Implement changes, redeploy | Tier 1 + affected Tier 2 + Tier 3 |

**No rollback** — sandbox is safe, fixes are additive.

---

## Notes

- This command processes ONE phase at a time — not the entire feature
- Each phase is a complete PIV loop with three validation gates
- The phase plan is self-contained — Claude can run this in a fresh context window
- Test class consolidation: ONE test class per Apex class. Consolidate during final phase if multiple were created across phases.
- Master plan is updated automatically at completion — no manual tracking needed
- If execution is interrupted (session timeout, etc.), re-run the same phase plan file — it will re-read the tasks and can pick up where it left off
- Browser automation is preferred for E2E testing; guided CLI is the fallback
- Deploy order within a phase follows the standard convention: Objects/Fields → Profile → FlexiPage → Layouts → PermSets → Sharing Rules
