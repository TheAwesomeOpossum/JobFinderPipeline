# SF Init Project

Run this command to bootstrap a new Salesforce project from scratch. This is the first command to run when starting a new SF project with this template. It creates the SFDX project structure (if needed), connects to the org, runs a full context scan across all registered skills, and produces a comprehensive org architecture summary.

**Usage:** `/sf-init-project <alias>` — alias is optional; you will be prompted if not provided.

---

## Phase 0: Pre-Flight Checks

Before doing anything, verify the environment is ready.

### Step 0a: Verify SF CLI

```bash
sf version
```

- If this command fails: **stop immediately** and instruct the user to install the Salesforce CLI: `npm install -g @salesforce/cli`
- Display the installed version for the record

### Step 0b: Check for Existing SFDX Project

Look for `sfdx-project.json` in the current working directory.

- **If `sfdx-project.json` exists:**
  - Log: "SFDX project already exists. Skipping project creation."
  - Read and display the project name and source API version from the file
  - Proceed to Phase 1

- **If `sfdx-project.json` does NOT exist:**
  - Ask the user: "No SFDX project found in this directory. Would you like to create one? If yes, what should the project name be?"
  - Wait for user response
  - Run:
    ```bash
    sf project generate --name {project-name}
    ```
  - Verify the project was created by checking for `sfdx-project.json`
  - If project generation fails: display the error and stop

### Step 0c: Verify Template Directories

Check that the template's `skills/` and `commands/` directories exist (they are part of this template and should be present).

```bash
ls -d skills/ commands/
```

- If `skills/` is missing: warn "skills/ directory not found — skill-based context scanning will be unavailable"
- If `commands/` is missing: warn "commands/ directory not found — this is unexpected for this template"
- Neither missing directory is fatal — proceed with warnings

## Phase 1: Connect to Org

### Step 1a: Determine Alias

- If `$ARGUMENTS` is provided and non-empty, use it as the target alias
- If `$ARGUMENTS` is not provided:
  - Ask the user: "What alias would you like to use for this org connection? (e.g., 'myproject-dev', 'client-sandbox')"
  - Wait for user response and use it as the alias

### Step 1b: Check Existing Connection

Attempt to display the org to see if it is already authenticated:

```bash
sf org display --target-org <alias> --json
```

- **If the command succeeds:** the org is already connected
  - Extract and capture from the JSON output:
    - `instanceUrl`
    - `apiVersion`
    - `username`
    - `id` (orgId)
  - Determine `orgType`:
    - If `instanceUrl` contains `.sandbox.` or `.cs` → Sandbox
    - If `instanceUrl` contains `.scratch.` → Scratch
    - Otherwise → Production
  - Log: "Org '{alias}' is already authenticated. Reusing existing connection."
  - Skip login, proceed to Step 1d

- **If the command fails:** the org is not authenticated, proceed to Step 1c

### Step 1c: Authenticate to Org

Run the web login flow:

```bash
sf org login web --alias <alias>
```

- Wait for the user to complete the browser-based login
- Once login completes, re-run:
  ```bash
  sf org display --target-org <alias> --json
  ```
- Extract and capture: `instanceUrl`, `apiVersion`, `username`, `id` (orgId)
- Determine `orgType` using the same logic as Step 1b
- If login or display fails: display the error and stop

### Step 1d: Set Default Org

```bash
sf config set target-org=<alias>
```

Log the confirmation:
```
Org connection confirmed:
  Alias:        {alias}
  Org ID:       {orgId}
  Org Type:     {orgType}
  Instance URL: {instanceUrl}
  Username:     {username}
  API Version:  {apiVersion}
  Set as default target org: yes
```

## Phase 2: Initialize Context Directory

Create the persistent context directory structure. This is where all cached org state will live.

### Step 2a: Create Directory Structure

Create these directories if they do not already exist:

```
context/
context/{alias}/
context/{alias}/objects/
context/{alias}/audit/
```

If `context/` already exists (e.g., from a previous run), that is fine — proceed without error.

### Step 2b: Write or Update INDEX.md

Read `context/INDEX.md` if it exists. If not, create it with this template:

```markdown
# Org Context Index

_Auto-generated by sf-init-project. Do not hand-edit._

## Connected Orgs

| Alias | Org ID | Instance URL | Username | Last Full Scan | Last Freshness Check | Context Path |
|---|---|---|---|---|---|---|
| {alias} | {orgId} | {instanceUrl} | {username} | {TIMESTAMP} | _(not yet run)_ | context/{alias}/ |
```

If `INDEX.md` already exists, check if a row for this alias is present:
- If present: update the row with current connection info
- If not present: append a new row

### Step 2c: Write Initial META.md

Write `context/{alias}/META.md`:

```markdown
# Org Meta — {alias}

## Connection Info
- Alias: {alias}
- Org ID: {orgId}
- Instance URL: {instanceUrl}
- Username: {username}
- API Version: {apiVersion}
- Org Type: {orgType}

## Scan History

| Timestamp | Type | Summary |
|---|---|---|
```

If `META.md` already exists, do NOT overwrite it — the scan history table contains valuable history. Instead, update only the Connection Info section if values have changed.

## Phase 3: Run Full Object Scan

Execute the base-layer object inventory. This mirrors the logic from `sf-get-existing-org-object-context` Phases 2-3.

### Step 3a: List All Custom Objects

```bash
sf sobject list -s custom --json --target-org <alias>
```

- Parse the JSON output to get a list of all custom object API names
- Count total custom objects found

### Step 3b: Identify Managed Packages

Analyze the custom object list for namespace prefixes:
- Any object matching `{Namespace}__{ObjectName}__c` has a namespace prefix
- Group objects by namespace prefix
- Build a managed packages table:

| Namespace | Object Count | Example Objects |
|---|---|---|
| AcctSeed | 42 | AcctSeed__Journal_Entry__c, AcctSeed__Billing__c |
| SBQQ | 28 | SBQQ__Quote__c, SBQQ__QuoteLine__c |
| FSL | 15 | FSL__Scheduling_Policy__c |

- Separate custom objects into:
  - **Org-built objects** (no namespace prefix): objects like `My_Custom_Object__c`
  - **Managed package objects** (with namespace prefix): objects like `AcctSeed__Journal_Entry__c`

Log: "{N} custom objects found total ({M} org-built, {P} managed from {K} packages)"

### Step 3c: Write Objects Inventory

Write `context/{alias}/objects/_inventory.md`:

```markdown
# Objects Inventory — {alias}

_Last scanned: {TIMESTAMP}_
_Source: sf-init-project_

## Detected Managed Packages

| Namespace | Object Count | Description |
|---|---|---|
| {namespace} | {count} | {inferred description or "Unknown package"} |

## Detected Naming Conventions

Analyze org-built object names for patterns:
- Prefix patterns (e.g., all objects start with `APP_`)
- Suffix patterns
- Separator usage (underscores vs. camelCase)
- Abbreviation conventions

## Custom Object Inventory

| Object API Name | Namespace | Org-Built | Last Modified | In Local Files |
|---|---|---|---|---|
| {ObjectName__c} | {namespace or blank} | {Yes/No} | {if available} | {Yes/No} |
```

Include ALL custom objects (both org-built and managed) in the inventory table.

## Phase 4: Run Registered Skill Full Scans

Discover all registered skills and run their full inventory queries to build a comprehensive context cache.

### Step 4a: Discover Registered Skills

Read all files matching `skills/*/SKILL.md`.

For each file, look for a `## Context Specification` block. Extract:
- `metadata_type` — the type(s) this skill tracks
- `context_path` — where inventory files live (e.g., `{alias}/flows/`)
- `inventory_file` — path to `_inventory.md`
- `detail_file_pattern` — path pattern for detail files (if specified)
- **Full Inventory Query** — the query with no date filter (gets everything)
- API type: `tooling API` or `standard API` or `metadata API retrieve`
- **Naming Convention Detection** section — what naming patterns to analyze

Log which skills were discovered:
```
Discovered {N} registered skills for full scan:
  - sf-flows → Flow (tooling API)
  - sf-apex-classes → ApexClass (tooling API)
  - sf-validation-rules → ValidationRule (tooling API)
  - sf-permissions → Profile, PermissionSet (standard API)
  - sf-trigger-patterns → ApexClass, ApexTrigger (tooling API)
  - sf-data-architecture → RecordType, CustomLabel, GlobalValueSet, FieldSet, PlatformEvent (mixed)
  - sf-layouts → Layout, FlexiPage, CompactLayout (tooling API)
  - sf-automation-legacy → WorkflowRule, WorkflowFieldUpdate, WorkflowAlert (tooling API)
  - sf-ui-components → LWC, Aura, ApexPage, QuickAction, CustomTab (tooling API)
  - sf-integration → NamedCredential, RemoteSiteSetting, CspTrustedSite, ExternalDataSource (tooling API)
  - sf-fsl → ServiceTerritory, WorkType, SkillRequirement, ServiceResource, OperatingHours (standard API)
  - sf-cpq → SBQQ__ProductRule__c, SBQQ__PriceRule__c, SBQQ__QuoteTemplate__c (standard API)
  - sf-experience-cloud → Network, ExperienceBundle, NavigationMenuItem (mixed)
  - sf-reporting → Report, Dashboard, ListView (standard API)
  - sf-email-notifications → EmailTemplate, CustomNotificationType (mixed)
  - sf-security-advanced → PermissionSetGroup, DuplicateRule, MatchingRule (mixed)
  - sf-assignment-rules → AssignmentRule, AutoResponseRule, EscalationRule (metadata API retrieve)
  [... any others found ...]
```

### Step 4b: Run Full Inventory Queries

For each registered skill, execute the following sequence:

1. **Create context directory:** `context/{alias}/{context_path}/` (if not present)

2. **Run the Full Inventory Query:**
   - If skill specifies `tooling API`:
     ```bash
     sf data query \
       --query "{Full Inventory Query}" \
       --use-tooling-api \
       --json \
       --target-org <alias>
     ```
   - If skill specifies `standard API`:
     ```bash
     sf data query \
       --query "{Full Inventory Query}" \
       --json \
       --target-org <alias>
     ```
   - If skill specifies `metadata API retrieve`, see Step 4c below

3. **Parse the query results:**
   - Extract all rows returned
   - Count total items found

4. **Analyze naming conventions:**
   - Examine all API names / DeveloperNames returned
   - Detect patterns per the skill's `Naming Convention Detection` section:
     - Prefix patterns (e.g., all flows start with `RT_` for record-triggered)
     - Suffix patterns
     - Separator usage
     - Categorization patterns (e.g., test classes ending in `_Test` vs `Test`)
   - Record detected patterns with counts and percentages

5. **Write the `_inventory.md` file:**
   ```markdown
   # {Metadata Type} Inventory — {alias}

   _Last scanned: {TIMESTAMP}_
   _Source: sf-init-project_
   _Skill: {skill-name}_

   ## Detected Naming Conventions
   {patterns found, with counts and percentages}

   ## Inventory

   | {columns per skill's Inventory Columns spec} |
   |---|
   | {data rows} |
   ```

6. **Write detail files** if the skill specifies them (e.g., sf-flows for record-triggered flows):
   - Use the skill's `detail_file_pattern` with `{ApiName}` replaced
   - Write one file per detail item, formatted per the skill's `Detail File Sections`

7. **Handle errors gracefully:**
   - If the query fails with "object type not found" or similar (common for FSL, CPQ, Experience Cloud objects that require specific licenses):
     - Log: "SKIPPED: {skill-name} — {metadata_type} not available in this org (likely missing license or managed package)"
     - Do NOT create the context directory or inventory file for skipped skills
     - Do NOT abort the overall scan — continue to the next skill

Log progress after each skill completes:
```
  [1/{total}] sf-apex-classes: 142 classes found (38 test, 12 batch, 8 schedulable, 84 other)
  [2/{total}] sf-flows: 23 active flows found (15 record-triggered, 5 screen, 3 scheduled)
  [3/{total}] sf-validation-rules: 67 validation rules across 18 objects
  [4/{total}] sf-permissions: 14 permission sets, 8 profiles
  [5/{total}] sf-fsl: SKIPPED (FSL not installed)
  [6/{total}] sf-cpq: SKIPPED (SBQQ namespace not found)
  ...
```

### Step 4c: Handle Metadata API Skills

Some skills (e.g., sf-assignment-rules) require Metadata API retrieve rather than SOQL queries. For these:

1. Run the retrieve command specified in the skill's Context Specification:
   ```bash
   sf project retrieve start --metadata "{MetadataType}" --target-org <alias> --json
   ```

2. Parse the retrieved XML files from the local project directory

3. Write the inventory file from the parsed XML, following the same format as SOQL-based skills

4. If the retrieve fails (metadata type not present), log a warning and skip — same as Step 4b error handling

### Step 4d: Collect Skill Scan Summary

After all skills have completed, build a summary data structure:

  - sf-validation-rules: 67 validation rules found across 18 objects
  - sf-permissions: 14 permission sets, 8 profiles found
  - sf-layouts: 45 layouts, 12 FlexiPages, 3 compact layouts

  - sf-ui-components: 12 LWC, 5 Aura, 8 VF Pages, 15 Quick Actions

  - sf-integration: 3 named credentials, 5 remote site settings
  - sf-reporting: 87 reports, 12 dashboards, 156 list views
  - sf-email-notifications: 18 email templates, 3 custom notification types
  - sf-security-advanced: 4 permission set groups, 2 duplicate rules

## Error Handling

Throughout all phases, follow these error handling principles:

- **Fatal errors** (stop execution):
  - SF CLI not installed
  - Org authentication fails (login flow aborted or credentials invalid)
  - Cannot create project directory (permissions issue)

- **Non-fatal errors** (warn and continue):
  - Individual skill query fails (metadata type not available in org)
  - Metadata API retrieve fails for optional types
  - Managed package detection finds unrecognized namespace
  - Detail file write fails for a specific item

- **Idempotency:** This command is safe to re-run at any time. It will:
  - Skip project creation if `sfdx-project.json` exists
  - Reuse existing org connection if already authenticated
  - Overwrite inventory files with fresh data
  - Append (not overwrite) scan history in META.md
  - Update (not duplicate) INDEX.md rows

## Phase 7: Prime Session

After all scanning and context writing is complete, automatically run the `/sf-prime` Phase 4 + Phase 5 logic:

1. Output the concise org state dashboard (metadata counts, complexity, automation density, naming conventions, freshness)
2. Display the session guidance with available actions

This ensures the user immediately sees what the org looks like and what they can do next, without needing to run `/sf-prime` as a separate command. The init flow seamlessly transitions into a primed session.

## Notes

- This command is safe to re-run — it will refresh all context files while preserving scan history
- If org connection already exists, it reuses it (no re-login required)
- Managed package detection helps Claude understand what is org-built vs. package-managed
- The naming convention summary is critical — all future implement commands should follow these detected patterns to maintain codebase consistency
- If the scan takes too long on a large org, individual skills can be skipped by removing them from the `skills/` directory
- The architecture summary file (`context/{alias}/audit/architecture-summary.md`) can be re-read in future sessions to quickly understand the org without re-scanning
- Context files written here are a cache — they are re-derivable from the org at any time via re-running this command or `sf-get-existing-org-object-context`
- The `context/` directory should be committed to version control so team members share the same cached context
